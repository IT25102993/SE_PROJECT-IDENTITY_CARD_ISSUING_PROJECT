1Schema definition

The whole database in one block. Attribute order follows the physical table definition in config/db.js, which is the schema the running application actually uses.

Two schemas exist in this repository, and they are not identical. The authoritative runtime schema is the MySQL DDL in server/src-nodejs/config/db.js (plus its incremental ALTER TABLE migrations). identity_card_system.sql is the older T-SQL/SSMS script. Three relations (account_deletion_requests, dispatch_records) exist only in the MySQL schema; payments exists only in the T-SQL script. documents differs between them (MySQL adds file_name and file_size). Wherever the two disagree, this document follows MySQL and marks the T-SQL-only material explicitly.
The MySQL DDL declares no foreign keys at all. config/db.js creates nine tables with primary keys, UNIQUE declarations, ENUM domains and secondary INDEX clauses, but zero FOREIGN KEY clauses. The nine named foreign keys documented in section 4 are declared only in identity_card_system.sql; the ON DELETE behaviour they describe is therefore the design intent, and in the deployed MySQL database it currently rests on application code rather than on the engine. Spring Data JPA inherits the same gap, since none of the nine entity classes declares @ManyToOne, @OneToOne or @JoinColumn: each stores a plain Long such as private Long applicantId.

* Logical reference only. Six attributes point at a parent but carry no declared constraint: verifications.applicant_id (a deliberate denormalised shortcut for citizen-scoped history), verifications.verified_by, dispatch_records.application_id, dispatch_records.dispatched_by, account_deletion_requests.user_id and account_deletion_requests.processed_by. The last five are unconstrained simply because their parent relations are MySQL-only and the MySQL DDL never declares a foreign key. Nothing at the database level prevents an orphaned value in any of them; the application is responsible for supplying a valid key.

Relation 1 of 9

USERS

Authentication and authorisation. One row per human account. Candidate keys: {user_id}, {username}, {email}.

Registered actors of the workflow. Deliberately disjoint from applicants: an account is an identity you log in with, an applicant is a citizen you issue a card to.

Primary keys

Ten surrogate integer keys, one per relation. Every attribute name follows <entity>_id and every value is generated by the database (AUTO_INCREMENT in MySQL, IDENTITY(1,1) in T-SQL), so keys are monotonic and never reused.

Candidate keys

Seven in total. Six are declared UNIQUE: username, email, national_id_number, card_number, identity_cards.application_id and transaction_ref. The seventh is the composite {application_id, dispatched_at} on dispatch_records, which is a candidate key by construction but is deliberately not declared, since a re-dispatch of the same application must create a second row.

CASCADE is used only where the child has no independent existence: a document without an application is meaningless, so removing the parent must remove it.
SET NULL is used for actor references. A card must still show that it was issued after the issuing officer's account is removed, and the audit trail must outlive the individual it records.
NO ACTION is used on identity_cards.applicant_id to block deleting a citizen who holds a legally issued card. Closure instead runs through the account_deletion_requests workflow.
No ON UPDATE clause is written anywhere. T-SQL defaults to NO ACTION on update and MySQL defaults to RESTRICT, so surrogate keys can never be re-pointed in either schema. Because the clauses are absent rather than explicit, they differ between the two dialects even though the observable behaviour is identical.
Six of the fifteen references are unconstrained in practice. The bottom six rows above have no FOREIGN KEY clause anywhere in the repository, so a deleted parent can leave an orphan child. This is the single most significant weakness in the schema, and it is invisible to both config/db.js and the JPA entities, neither of which declares any relationship mapping.
Cardinality is enforced structurally where it can be. The 1:1 from applications to identity_cards holds because of the UNIQUE on application_id, which is declared in both schemas. Every other cardinality is only implied by the shape of the model, not enforced.

8Schema certification

Normal form: 5NF. Every relation satisfies 1NF (atomic attributes, no repeating groups), 2NF (all dependencies are on the whole key, guaranteed by single-attribute surrogate keys), 3NF and BCNF (the only determinants are candidate keys, so there is no transitive dependency), 4NF (no residual multi-valued dependency) and 5NF (no non-trivial join dependency).
Lossless and dependency-preserving. Every decomposition joins a child to its parent on the parent's key, so no tuple is lost and no spurious combination can be fabricated. Every remaining functional dependency can still be enforced by a constraint on a single relation.
Documented deviations. Three deliberate departures from strict normalization are recorded and justified in DATABASE_DOCUMENTATION.html section 7.8: the composite applicants.address string, the applications.assigned_officer name column, and the denormalised convenience pointer verifications.applicant_id. The remaining duplicates in dispatch_records and account_deletion_requests are immutable historical snapshots required by courier and legal-evidence rules, not redundancy defects.
Model shape. The schema is a tree: users and applicants are the roots, applications is the aggregate root, and the remaining six relations hang off it. There is no cyclic dependency, so join order is always derivable and the backup restore order is deterministic.
The 5NF claim is about structure, not about enforcement. Normalization is a property of the relation definitions and holds on paper. It does not mean the deployed MySQL database enforces what it describes: that database has no foreign keys, and Hibernate's ddl-auto=update will not add them, because the entities declare plain Long fields instead of associations. Closing the gap means adding FOREIGN KEY clauses to the nine MySQL CREATE TABLE statements in config/db.js and mapping the relationships with @ManyToOne / @OneToOne in the nine entity classes.
