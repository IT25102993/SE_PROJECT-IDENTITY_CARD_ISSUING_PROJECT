1. Overview & Scope

The NexusGov Smart Identity Card Issuing System is a role-governed web platform that digitises the complete lifecycle of a national identity card: citizen registration, document upload, AI-assisted verification, officer approval, card generation, printing, dispatch and audit. The database is the single source of truth for all of it.

This document describes, in full:

  • The storage engine and its configuration (MySQL/InnoDB primary, H2 in-memory fallback).
  • The conceptual model (ER diagram) and the resulting relational schema.
  • A rigorous normalization analysis deriving every table from the raw business data, with the functional dependencies, candidate keys, normal forms and the anomalies each step removes.
  • A column-level data dictionary for all ten tables (nine live in the MySQL runtime, one exists only in the T-SQL/SSMS script).
  • Keys, constraints, indexes, referential actions, migrations, triggers, backup strategy, security and performance notes.

Design principles applied

  1. One real-world entity per table; no "god table" combining users, applications and cards.
  2. Every non-key attribute depends on the whole key, and on the key alone (3NF / BCNF).
  3. Repeating groups (documents, verifications, payments) decomposed into child relations.
  4. Derived values are never stored; immutable snapshots are stored deliberately and labelled.
  5. Business vocabulary constrained at the storage layer (ENUM / CHECK), not only in the UI.
  6. Audit trail modelled as an append-only relation, never updated or deleted.
  7. Passwords never stored in plaintext; bcrypt hashes only.

6.2 Indexing rules followed

  • Every foreign-key column is indexed or is itself UNIQUE. This is mandatory: InnoDB needs an index on the referencing side, otherwise a parent delete must scan the child table and a parent update must lock it.
  • Unique business keys carry the most value. Login, NID duplicate check and card validation are the highest-frequency queries in the system, and each is served by a unique index rather than a full scan.
  • No redundant overlapping indexes. Only single-column indexes exist because no current query filters on two of these columns together. Past roughly 105 rows in verifications, the two single indexes should be replaced by one composite (applicant_id, application_id).
  • No index on applications.status despite heavy status filtering. The dashboard queries filter status together with a date range, so a selective composite (status, submitted_at) is the correct choice at that point. This is a documented trade-off, not an oversight.
  • Binary content is never stored in the database. documents.file_path holds only a pointer, so the table stays narrow and cache-resident while the files live under server/uploads/documents/.

7. Normalization: Foundations

7.1 Why normalize

Normalization organises attributes and relations so that each fact is stored exactly once, in exactly one place. It is a redundancy control derived directly from Codd's relational model. Redundant storage is not merely wasteful, it is actively dangerous, because the copies drift apart. Three anomalies follow:

Insertion anomaly

A fact cannot be stored without storing some other fact. A new document type, for example, cannot be recorded unless an application using it already exists.

Deletion anomaly

Deleting one fact silently destroys another. Deleting a citizen's last application destroys their NID and address.

Update anomaly

One logical change requires updating many rows. An officer's name change means rewriting 200 application rows; miss one and the database contradicts itself.

7.2 The normal-form ladder

NFFormal requirementPlain meaning
1NFEvery attribute is atomic (indivisible); no repeating groups; every tuple uniquely keyed.No lists. No first_name, last_name packed into one "name" column. No doc1, doc2, doc3 columns.
2NF1NF and every non-prime attribute is fully dependent on every candidate key.Nothing is stored merely because it happens to sit beside part of the key. Only meaningful for composite keys.
3NF2NF and no transitive dependency: no key -> X -> Y among non-prime attributes.Knowing the key gives you the value, and that value tells you nothing you did not already know.
BCNF3NF and every determinant is a superkey.Stricter than 3NF: a determinant can never predict a non-key attribute unless it is itself a key.
4NFBCNF and no non-trivial multi-valued dependency.Two independent "many" facts about the same key must live in separate relations.
5NF4NF and no non-trivial join dependency.Every join dependency is implied by candidate keys; nothing must be reassembled from three relations.
Terminology used below Candidate key a minimal superkey. Prime attribute one that appears in some candidate key. Non-prime attribute any other attribute. Prime determinant a non-superkey attribute that determines something, the only possible cause of a BCNF violation. Lossless join the decomposition preserves all information. Dependency preservation every original dependency can still be enforced with constraints on a single relation alone.

7.4  1NF: First Normal Form

Rules applied

  1. Split every non-atomic attribute into atomic components: Full_Name -> first_name, last_name. Address stays one atomic string, with the reasoning recorded in section 7.6.
  2. Eliminate every repeating group by giving each repetition its own row in its own relation: documents, verifications, payments.
  3. Introduce a unique tuple identifier for every relation: a surrogate INT AUTO_INCREMENT key.
  4. Ensure every column holds a single value and no row depends on its position in the table.

7.5  2NF: Second Normal Form

Prerequisite

2NF is only violated by composite keys. After 1NF the only relation whose candidate key has more than one attribute is the one describing documents inline with their application:

DOCUMENT_1NF' ( application_id, document_type, file_name, file_path, file_size, uploaded_at ) --------- composite candidate key: { application_id , document_type } --------- R3's key is chosen as the surrogate { document_id } -> no partial dependence remains. fd1: { application_id , document_type } -> file_name, file_path, file_size, uploaded_at PARTIAL dependence on application_id alone fd2: application_id -> (nothing about the file: file attributes vary per document) OK already full

file_name, file_path, file_size and uploaded_at describe one file, not "one document type belonging to application X". They depend on only part of the composite key: a textbook partial dependency. The identical defect existed in UNF for the bot-verification block (bot_verified, bot_score, bot_notes, bot_verified_at) and for the payment block.

Decomposition performed (lossless and dependency-preserving)

  1. documents(document_id PK, application_id FK, document_type, file_name, file_path, file_size, uploaded_at) — replace the composite key with a surrogate, so every dependency is on the whole key.
  2. verifications(verification_id PK, application_id FK, applicant_id FK, method, result, passed, score, notes, verified_by, verified_at) — the bot block becomes an independent child relation.
  3. payments(payment_id PK, application_id FK, amount, payment_method, payment_status, transaction_ref, paid_at).
  4. Applicant identity is moved out of applications into applicants. This is the partial-dependency fix for the demographic block: since {applicant_id} -> first_name, last_name, dob, gender, address, phone, email, those attributes depend on a proper subset of the application's natural key and therefore cannot live in the application relation.
  5. Card attributes are moved out into identity_cards, because {application_id} -> card_number, issue_date, expiry_date, card_status depends on a subset: an application may have zero or one card, and the card facts exist only once a card is issued.
  6. Authentication data is moved out into users, leaving processed_by as a bare key reference.
  7. Operational concerns are split out into dispatch_records, account_deletion_requests and audit_logs, each attached to exactly one parent.

7.6  3NF: Third Normal Form

3NF asks whether any non-prime attribute determines another non-prime attribute, that is, whether a transitive dependency exists. Three such chains existed in the 2NF schema.

Violation 1: the officer chain

applications.assigned_officer -> users.role, users.email, users.full_name via users.full_name chain: {application_id} -> assigned_officer -> { full_name, role, email } TRANSITIVE DEPENDENCY = 3NF VIOLATION

The officer's role, email and password hash are facts about the person, not about the application they happened to process. Storing the officer's name on the application duplicates it, and an officer rename becomes a 200-row UPDATE. Fix: users already exists, so reduce applications.processed_by to a bare foreign key to users.user_id and drop the assigned_officer name column, joining to users.full_name at read time. The display requirement is met by a join, not by storage.

Violation 2: the applicant chain

applications.application_id -> applicant_id -> { first_name, last_name, date_of_birth, gender, address, phone_number } TRANSITIVE DEPENDENCY = 3NF VIOLATION

Fix (already applied in the 2NF decomposition): hoist the entire dependent group into applicants and keep only the key applicant_id in applications. The chain is absorbed by a foreign key rather than by storage, so no transitive dependency is written down.

Violation 3: the location chain, identified and consciously accepted

applicants.address -> city -> district -> province -> region_code chain: {applicant_id} -> address -> city -> district -> province TRANSITIVE DEPENDENCY if decomposed

A strict 3NF treatment would decompose this into address(city_id, street, ...), city(district_id, city_name), district(province_id, ...), province. The team evaluated this and chose not to, for a documented reason: the address is a free-form mailing block used only for printing and courier delivery. It is never joined on, aggregated by, or reported across, and Sri Lankan administrative boundaries change far more often than this database is redeployed, so each boundary change would force a data migration across every applicant row. This is a conscious, justified 3NF deviation, mitigated by keeping the value atomic in a single attribute. If regional reporting becomes a requirement the correct fix is to add a separate optional regions dimension plus a region_id on applicants, not to over-normalise an atomic string today.

7.7  BCNF, 4NF and 5NF

BCNF is the strict form: every determinant must be a superkey. Because the 3NF audit above found that every determinant in every relation is already a candidate key, no BCNF violation can exist. The schema is in BCNF.

4NF is likewise satisfied. The two independent repeating groups that coexisted inside the UNF form ("many documents per application" and "many verification attempts per application") are now separate relations. No relation retains a multi-valued dependency of the form application_id ->-> document_type and independently application_id ->-> verification_result.

5NF is satisfied trivially. The model is a tree of parent-child relations plus one 1:1 leaf (applications to identity_cards). There is no ternary relationship that would create a non-trivial join dependency, so no relation ever has to be reassembled from three others.

10. Integrity & Constraints

10.1 Four kinds of integrity

KindDefinitionHow it is enforced here
Entity integrityEvery row must be uniquely identifiable.Surrogate primary key on every table, NOT NULL by definition of a PK.
Referential integrityEvery foreign key value must exist in the parent, or be NULL.Eleven declared foreign keys with explicit ON DELETE actions, listed in section 5.2.
Domain integrityEvery value must come from the attribute's permitted domain.ENUM types, CHECK constraints, length limits, and NOT NULL where a value is mandatory.
User-defined integrityBusiness rules beyond the above.Service-layer precondition checks inside transactions, listed in section 5.4.

10.2 Constraint enforcement points

In the database (declarative)

  • Primary keys, unique keys, foreign keys
  • ENUM domains for role, status, gender, method, result, payment_method
  • NOT NULL on every mandatory attribute
  • DEFAULT CURRENT_TIMESTAMP on all created/submitted timestamps
  • Auto-maintained updated_at

In the service layer (imperative)

  • Card issuance gated on an approved application
  • Ten-year validity arithmetic
  • Bot score threshold of 80 for automated pass
  • One active card per applicant
  • Audit-log write paired with every state change
  • Role checks on every mutating endpoint
JPA mapping note In the Spring Boot JPA entities, inter-entity links are expressed as plain scalar Long identifier columns rather than @ManyToOne associations, and status / role are String rather than Java enum types. Consequently Hibernate does not emit database-level foreign keys, and the ENUM/CHECK domains are only enforced when Hibernate's ddl-auto=update first creates the tables. Recommendation: deploy the explicit DDL from section 12 so the constraints exist independently of the ORM, and treat the JPA layer as a mapping convenience rather than the schema authority.

13. Migrations & Triggers

13.1 Idempotent schema creation

Boot-time DDL uses CREATE TABLE IF NOT EXISTS throughout, so the application is safe to restart against an existing database. Table creation is dependency-ordered: users and applicants first, then applications, then the child relations.

13.2 Incremental migrations applied at boot

-- 1. Role vocabulary evolution (three-step, data-preserving)
ALTER TABLE users MODIFY COLUMN role
  ENUM('Admin','Officer','Form-Officer','Document-Officer',
       'Approver','Operational','Citizen') NOT NULL DEFAULT 'Citizen';
UPDATE users SET role='Form-Officer' WHERE LOWER(role)='officer';
ALTER TABLE users MODIFY COLUMN role
  ENUM('Admin','Form-Officer','Document-Officer',
       'Approver','Operational','Citizen') NOT NULL DEFAULT 'Citizen';

-- 2. Widen the application workflow vocabulary
ALTER TABLE applications MODIFY COLUMN status
  ENUM('Pending','Approved','Rejected','Processing','Printed','Issued',
       'Dispatched','Verification-Passed','Documents-Required') NOT NULL DEFAULT 'Pending';

-- 3. New relations and columns for pre-existing databases
CREATE TABLE IF NOT EXISTS dispatch_records ( ... );
ALTER TABLE applicants ADD COLUMN photo_path VARCHAR(255) NULL;
ALTER TABLE applications ADD COLUMN assigned_officer   VARCHAR(100) NULL;
ALTER TABLE applications ADD COLUMN application_reason VARCHAR(100) NULL;
ALTER TABLE applications ADD COLUMN marital_status     VARCHAR(50)  NULL;
ALTER TABLE applications ADD COLUMN service_type ENUM('Normal','1-Day') NOT NULL DEFAULT 'Normal';

-- 4. The 2NF migration: move bot verification out of `applications`
--    into the dedicated `verifications` relation
INSERT INTO verifications (application_id, applicant_id, method, result,
                           passed, score, notes, verified_at)
SELECT application_id, applicant_id, 'AI-BOT',
       CASE WHEN bot_score >= 80 THEN 'Verified'
            WHEN bot_score  >  0 THEN 'Flagged'
            ELSE 'Inconclusive' END,
       COALESCE(bot_verified, 0), COALESCE(bot_score, 0),
       bot_notes, bot_verified_at
FROM  applications
WHERE (bot_verified IS NOT NULL OR bot_score IS NOT NULL
    OR bot_notes   IS NOT NULL OR bot_verified_at IS NOT NULL)
  AND application_id NOT IN (SELECT DISTINCT application_id FROM verifications);

ALTER TABLE applications DROP COLUMN bot_verified;
ALTER TABLE applications DROP COLUMN bot_score;
ALTER TABLE applications DROP COLUMN bot_notes;
ALTER TABLE applications DROP COLUMN bot_verified_at;
Why the migration is idempotent The NOT IN (SELECT application_id FROM verifications) guard prevents duplicating rows that were already migrated, and every ALTER is wrapped in a try/catch so a column that is already dropped or a role column that is already current is treated as success. This lets the same code run against a brand-new database and a two-year-old one without a version table.

16. Backup, Recovery & Retention

16.1 Strategy

The system uses a continuous, event-driven backup rather than a nightly schedule, because a card-issuing system's state is legally significant and a day of lost transactions is unacceptable.

TriggerActionArtefact
Any INSERT, UPDATE, DELETE, REPLACE or ALTERAutomatic backup of the full logical datasetbackup/database_backup.json and backup/database_backup.sql
Application start-upBaseline synchronisationBoth backup files refreshed
Start-up with an empty databaseAutomatic restore from the backup fileDatabase and in-memory store repopulated
MySQL connection lostDegrade to in-memory mode, keep serving, keep backing upBackup files remain current
MySQL restoredReconcile in-memory state back into MySQLSingle source of truth re-established

16.2 Why this matters for the relational design

  • Backups are logical (row-level), not physical, so the JSON artefact is a direct serialisation of the relations and stays readable if the schema later migrates.
  • Because the schema is in 3NF with no inter-table duplication, a restore of one relation is always consistent with the others. A denormalised design would have required cross-table repair logic during restore.
  • Foreign keys make the restore order deterministic, since the DAG in the ER diagram dictates users, applicants, applications, children.
  • The immutable relations (audit_logs, dispatch_records) are backed up but never rewritten, so a restore cannot silently lose audit evidence.

16.3 Recovery procedure

1. Stop the application servers.
2. Restore the SQL dump:
      mysql -u root -p identity_card_system < backup/database_backup.sql
   (or seed from scratch with identity_card_system.sql, which includes seed rows)
3. Start the servers; the boot routine verifies the schema and applies any
   pending migrations automatically.
4. Confirm the row counts of every table against the backup manifest.

17. Performance & Concurrency

17.1 Connection management

  • A single mysql2 pool of 15 connections serves the whole process; connections are created once and reused, never per request.
  • waitForConnections = true with an unbounded queue means a traffic burst degrades into latency rather than into errors.
  • TCP keep-alive prevents the classic PROTOCOL_CONNECTION_LOST failure caused by MySQL's wait_timeout closing idle connections.
  • Transient failures (ECONNRESET, ER_LOCK_DEADLOCK, EPIPE, ETIMEDOUT) trigger one automatic reconnect-and-retry, which covers a rolling MySQL restart without a user-visible error.

17.2 Transaction and locking practice

  • InnoDB supplies row-level locking and MVCC, so readers never block writers.
  • Multi-table operations (approve plus audit plus card insert) are wrapped in one transaction so partial states are impossible.
  • ON DELETE CASCADE is used sparingly; large cascading deletes are chunked in maintenance procedures to avoid long lock holds.
  • SELECT ... FOR UPDATE is used on identity_cards.application_id during issuance so two concurrent officers cannot mint two cards for the same application, even though the UNIQUE constraint would ultimately reject one.

17.4 Storage characteristics

  • utf8mb4 with 4-byte character support, so Sinhala, Tamil and emoji in names and remarks store correctly. This is why NVARCHAR in the T-SQL variant is not merely cosmetic.
  • DECIMAL(10,2) for money: exact base-10 arithmetic, no floating-point drift in reconciliation.
  • DATE rather than DATETIME for births, issue and expiry dates: half the storage and no meaningless time component.
  • DATETIME rather than TIMESTAMP for event times, to avoid the 2038 limit and the implicit timezone conversion of TIMESTAMP columns; UTC is enforced by the JDBC serverTimezone=UTC parameter.
  • Long text columns (remarks, notes, details) are stored off-page in overflow, keeping the frequently scanned index entries compact.
